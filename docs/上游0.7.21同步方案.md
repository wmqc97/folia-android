# 上游 v0.7.21 同步方案（folia-android）

本文记录把上游 `Timingyyds/folia-android` v0.7.21 同步进本仓库的结论、边界与执行顺序。

## 1. 上游源码的性质（实测）

| 事实 | 证据 |
| --- | --- |
| 上游仓库是**裁剪快照**，不是完整工程 | `src/stores/useSettingsUiStore.ts` 被 16 个上游文件 import，但仓库里没有这个文件 |
| 上游缺少本仓库已有的构建脚手架 | 上游无 `dev/`、`test/`、`electron/`、`api/`、`api-ts/`；但 `vite.config.ts` 却 import `./dev/i18n/traditionalLocalePlugin.mjs` 等 |
| 上游没有背屏歌词 | 上游 `src` 全树 `grep -ri rear` 只命中 ytm/i18n 无关词；安卓层无 `rear/`，改用 `coloros/ColorOsLyricBridge.java` |
| 上游在线音乐是**原生协议重写** | `src/audioNative/{qq,kugou,netease,bodian-impl}.ts` 取代本仓库 `src/audioNative/api/*.js`（打包的网页播放器） |
| 上游依赖有变化 | 新增 `qrcode`、`crypto-es`、`budoux`、`@paper-design/shaders`、`bgutils-js`、`youtubei.js`、`koffi`、`googlevideo`；去掉 `@fontsource/noto-sans-sc`、`buffer`、`@capacitor/browser` |

结论：**不能整树覆盖**。直接覆盖 `src/` 后 `tsc --noEmit` 从 148 个错误涨到约 700 个，且上游自身也不自洽。同步必须以本仓库为基座做**特性级移植**。

## 4. 在线音乐为什么不能整层覆盖（实测结论）

第 2 轮把 `services/onlineMusic/**` 整层换成上游后，src-only 错误 24 → 170，且**不可能靠修补收敛**，原因三条：

1. **omni API 改名**：`createQrLogin/checkQrLogin/cancelQrLogin/getLoginStatus/logout/getProviderUserPlaylists/getProviderCloudCollection/getProviderLikedSongs/getProviderLikedSongIds/normalizeCachedUser/normalizeCachedCollection/getProviderAvailability` 全部被删或改名，而本地账号/曲库层（`src/library/core/{bindings,contracts,model,services,state}`、`hooks/useKugouLibrary`+`useQqLibrary`+`useBodianLibrary` 共约 740 行）正是这些方法的唯一消费者。
2. **上游登录 UI 依赖公开仓库里不存在的模块**：`components/login/**` 会 import `library/core/account/account.contract`、`library/core/account/useLibraryAccount`、`components/modal/settings/kit/{kitTheme,motion}`、`types/loginFailure`、`utils/system/{outsideLink,clipboard}` —— 上游快照里一个都没有，无法编译也无法照抄。
3. 上游自己的 `omni.ts` 也缺依赖（`utils/likePresses`、`utils/errorText`，已从上游补齐，可继续用）。

因此**保留本地在线音乐子系统**，改为按 provider 替换**传输后端**：上游原生协议的入口是
`handleKugouEndpoint(endpoint)`、`handleNeteaseEndpoint(endpoint, limit?)`、`handleQqEndpoint(operation, path, params, payload, cookie)`，
吃的是「路径 + query」，与本地传输层的 `ENDPOINTS[operation]` 表同构 —— 把本地 `fetch(`${base}${path}?${query}`)` 那一处分流到原生入口，就能让 QQ/网易云/酷狗的请求与登录走原生协议，而 provider / hooks / 界面一行不动。

### 第 3 轮：传输后端已接通

- 新增安卓原生网络层 `FoliaBridgePlugin.java`（OkHttp + 系统 CookieManager，手动跟随重定向、逐跳写 Set-Cookie、支持 base64 二进制），并在 `MainActivity.onCreate` 里 `registerPlugin(FoliaBridgePlugin.class)`。okhttp 依赖本地 `app/build.gradle` 已有。
- 三个传输层在「没有 electron IPC、没有扩展桥、没有配置远端 API base」时（也就是安卓 APK 的默认情形）分流到原生协议：
  - `kugouTransport.requestKugou` → `executeNative`（含设备校验 `register_dev` 重试）
  - `qqTransport.requestQq` → `requestQqNative`
  - `services/netease.ts` 的请求核心 → `handleNeteaseEndpoint`
- `bootstrap.tsx` 装 `installNativeFetchShim()`：跨域请求统一走 FoliaBridge，登录态与系统 CookieManager 共用同一个罐。
- 会话键与 `providerStorage` 完全一致（`online_provider:<provider>:<key>`），所以原生层拿到的就是界面里登录出来的会话。

校验：`tsc --noEmit` 148（src-only 24，与基线持平）；`javac -XDshould-stop.at=PARSE` 对 `FoliaBridgePlugin.java` / `MainActivity.java` 零语法错误。

### 第 4 轮：波点接入 + 构建验证 + 登录契约核对

- `bodianTransport` 也接上原生分支（`handleBodianRequest` 的 `{ok,data}|{ok,error}` 与 `BodianBridgeResult` 同构），扩展桥路径保留为回退。
- **`vite build` 通过（exit 0）**：`FOLIA_BUILD_TARGET=capacitor FOLIA_DISABLE_PWA=1` 下整包可打包，说明 `audioNative/*`、四个传输层接线、fetch 桥没有循环依赖或解析失败。
- 登录契约已逐条核对（酷狗）：
  - `login_qr_key` 无参 → 原生 `/login/qr/key` 无参 ✅
  - `login_qr_create {key}` → 原生读 `params.key`，二维码 PNG 由 `qrcode` 在本地生成并回 `qrimg` ✅
  - `login_qr_check {key,qrcode}` → 原生读 `params.key ?? params.qrcode`，回 `{data:{status,token,userid,...}}`；本地 `kugouProvider` 正是按 `data.status`（0 过期 / 1 等待 / 2·3 已扫 / 4 成功）解析 ✅
  - 原生在 status=4 时把 `kg_mid`/`kg_dfid`/`token`/`userid` 一并写进 `providerStorage`，播放接口按这套设备字段校验 token
- **APK 构建被环境卡住（不是代码问题）**：`gradlew assembleDebug` 跑到 67 个 task 后失败在 `:capacitor-android:compileDebugJavaWithJavac`，报「无效的源发行版: 21」——本机只有 `C:/Android/jdk17`，而 `build-apk.sh` 自己找的是 `C:/Program Files/Eclipse Adoptium/jdk-21.0.12.8-hotspot`（本机不存在）。装好 JDK 21 后 `./build-apk.sh` 即可完成 Java 层验证。
