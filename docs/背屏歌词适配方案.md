# Folia 安卓版 · 小米背屏歌词移植适配方案

> 目标：把 Folia（本地/在线音乐播放器）改造成「主屏 = 切歌列表，背屏 = 歌词显示」的形态。
> 参考实现：`F:\Android\App\MiRoot`（小米 17 Pro 系列背屏增强工具，已跑通背屏投屏 + 歌词投影）。
> 本文档既是**方案**，也是**落地记录**：阶段 0～3 的代码已经进仓库，逐项状态见 §5，实施细节见 §12、§13。
> 状态：v7（阶段 0/1/2 已完成；阶段 3 的同步与交互已完成；背屏设置面板 / 一键投屏 / 外部广播已完成，见 §13.8–§13.12）

---

## 0. 一页速览（先看这个）

**这件事能不能做？能。** MiRoot 已经在真机上跑通了「把任意界面投到背屏 + 在背屏显示歌词」这条链路，其中**背屏用 WebView 承载自定义网页**的那一套（`WebPanelRearScreenActivity`）几乎就是 Folia 需要的形态。Folia 本身也是 WebView 应用，复用地基很好。

**已确认的决策：**

1. **权限通道**：Shizuku 为主，root 作为增强（root 优先，失败自动回退 Shizuku）。
2. **背屏形态**：做一套**背屏专用界面**——含**全部歌词效果**、**切歌**、**效果设置**；不显示主屏那些完整界面和设置。
3. **支持机型**：小米 17 Pro 系列 + 小米 18 Pro 系列（两代背屏形态接近）。
4. **背屏硬件**：左侧挖孔，**竖向排列的两个孔基本铺满左侧区域**（只有一点点显示）；左侧整条竖带直接不用。
5. **布局要求**：画布保持**整屏**（不收窄、不压缩字号），只把**渲染中心**右移安全带的一半，
   让主歌词落在右侧可见区里居中（做法见 §3.4）；背景可以**铺满/轻微越界**，
   歌词也可以轻微压到摄像头带（非主视角内容，接受）。
6. **触摸能力**：背屏**支持触摸**，只有**左侧摄像头区域不能触摸** → 控制面板放在背屏（但不得落在左侧竖带内）。
7. **字号**：背屏与主屏的歌词字号**各自独立**——背屏只有 347×212 CSS px，和主屏共用一份字号必然
   一头合适一头不合适（见 §13.6）。

**整体做法一句话：**
在 Folia 安卓原生层加一个「背屏 Activity」，用 Shizuku/root 投到 display 1，里面放一个 WebView 加载 Folia 自己的**背屏专用路由**（`?rear=1`）；主屏与背屏通过原生中转互相同步播放状态与设置。

**三条关键技术结论：**

1. **背屏内容**：复用 Folia 现有的歌词渲染与 visualizer 效果，新增一个「背屏专用」根组件与布局，而不是从零重写。
2. **状态同步**：复用 Folia 已有的「第二块屏靠事件流拿播放状态」模式（OBS 歌词源），把同一个 publisher 的载荷多推一路给背屏。
3. **左挖孔**：左侧留一条**固定宽度的安全带（实测 296px ≈105 CSS px）**，不做精细 cutout 适配；**背景铺满整屏，歌词画布也不收窄，只把渲染中心右移半个安全带宽度**，让主歌词在右侧可见区居中；**设置面板与触摸目标从安全带右侧开始**。

**当前进度（2026-10-14）：**

- 阶段 0（真机摸底）、阶段 1（原生投屏骨架）、阶段 2（背屏歌词渲染）**已完成**。
- 阶段 3（状态同步与交互）**代码已完成、本地探针已验证，尚未上真机验收**。
- 主屏入口（**播放页封面正中的背屏投屏按钮** + 设置卡片 + 命令面板）**已完成**（§13.9）。
- **背屏歌词与主屏字号独立**（§13.6）**已完成，并在 Xiaomi 17 Pro Max 上真机验证**。
- **背屏设置面板（6 页签精简版，去封面图）已完成**（§13.8），本地探针逐页验证通过。
- **「播放即自动投屏」开关、外部广播调用（START/STOP/TOGGLE）已完成**（§13.9 / §13.10）。
- **歌词布局改造为「渲染中心偏移」已完成并上真机验证**（§3.4 / §13.3）：不硬切割、也不整块平移，
  改为把**画布右缘外扩 `safeLeftCss`**（347 视口下宽度 453 = `right: -106px`），画布铺满整屏无缝隙，
  画布中心自己落到可见区中心，主歌词因此自动居中；本地探针在 14 个模式下量到中心误差 < 1px，
  小米 17 Pro Max 真机实测与探针一致。
- 未做：连续 20 次投屏压测、锁屏 / 常亮（阶段 4）。

**与初版方案的一处偏差（已按实现更新）：** 初版写的是「本地 HTTP + SSE 中转」，实际实现改为
**Capacitor 插件事件 + `evaluateJavascript`**：主屏 → 背屏走 `RearProjection.publishSnapshot`，
背屏 → 主屏走 `@JavascriptInterface` 回调 + `command` 事件。原因是两个 WebView 同进程、同 origin，
再起一个 HTTP 服务要多维护端口、Token 与生命周期，收益为零。

### 1.2 参考项目（MiRoot）

| 项 | 现状 |
|---|---|
| 形态 | 纯原生 Kotlin/Java 安卓应用（362 个 kt 文件），Compose + 传统 View 混用 |
| 包名 | `com.wmqc.miroot` |

**MiRoot 的投屏链路（这是要移植的核心）：**

```
入口（手势 / 广播 / 按钮）
   │
   ├─ 直启优先：am start --display 1 -n <包名/Activity>
   │      └─ 成功判据：轮询 am stack list，确认该 Activity 已在 display 1（约 600ms 内）
   │
   └─ 失败回退（锁屏 / 被系统拦截）：
          1) am start --display 0 -n <包名/Activity>   ← 主屏透明占位
          2) 轮询 am stack list 找到 taskId
          3) service call activity_task 50 i32 <taskId> i32 1   ← 把任务迁到 display 1
   │
   └─ 落屏后：禁用官方背屏中心 com.xiaomi.subscreencenter
              （否则官方背屏会抢占/覆盖投屏内容）
```

**MiRoot 已经处理好的坑（要继承的经验）：**

- 锁屏状态下 `am start --display 1` 会被系统 `ActivityStarterImpl` 直接 abort。**root 也绕不过**，只有 LSPosed 模块（REAREye）能解。
- 背屏物理圆角统一 **35dp**（`ProjectionHelper.REAR_SCREEN_CORNER_RADIUS_DP`），系统 API 在投屏场景常拿到主屏值，需要兜底。
- 背屏**左侧摄像头安全区**：MiRoot 硬编码 `277px`（设备密度约 2.83，约合 98dp）。
- 背屏**支持触摸**：MiRoot 的桌宠（点宠物/拖动/双击）、真心话转盘都依赖背屏触摸，验证了硬件可行。
- 各背屏 Activity 必须：`launchMode=singleInstance` + **独立 taskAffinity** + 完整 `configChanges`，并在 manifest 里声明 `miui.rear.policy`。
- 退出投屏时要恢复官方背屏中心，否则背屏会「卡死」在投屏页。

## 2. 目标形态

```
┌─────────────────────────┐        ┌────────────────────────────────┐
│  主屏（手机正面）        │        │  背屏（手机背面，display 1）    │
│                         │        │                                │
│  Folia 主界面            │  双向  │  ┃●┃（左侧竖排两孔，不可触摸）  │
│  = 歌单 / 切歌列表       │ ◀────▶ │  ┃●┃                           │
│  + 播放控制              │  同步  │       主歌词（右侧区域内居中）   │
│  + 「背屏歌词」开关       │        │       译文 / 下一句              │
│                         │        │  背景可铺满 / 轻微越界          │
└─────────────────────────┘        └────────────────────────────────┘
```

**需求拆解（已确认）：**

1. 主屏保持现有 Folia 界面（本身就是歌单 + 播放器），额外加「背屏歌词」开关与状态提示。
2. 背屏是**专用精简界面**，不是主屏的缩小版；不显示主屏的完整页面与完整设置。
3. 背屏**保留全部歌词效果**（即 Folia 现有的歌词特效 / visualizer 模式）。
4. 背屏支持**切歌**与**效果设置**（通过背屏触摸操作）。
5. 支持机型：小米 17 Pro 系列 + 小米 18 Pro 系列。
6. 背屏左侧是**竖排两个孔，基本铺满左侧区域**（那里只有一点点显示），所以整条左侧竖带**直接不用**——不放可读内容，也不放触摸目标。
7. **主歌词落在右侧可见区居中**：画布保持整屏，只把**渲染中心**右移半个安全带宽度（做法见 §3.4）。
8. 背景图层铺满整屏，允许轻微越界。
9. 通过 Shizuku（主）/ root（增强）完成投屏。

## 3. 技术方案

### 3.1 投屏通道：Shizuku 优先，root 增强 ✅已确认

| 方案 | 说明 | 定位 |
|---|---|---|
| **root（`su -c`）** | 最稳，重启后仍有效 | ✅ 首选通道（有 root 时自动用） |
| **Shizuku** | 免 root、免解锁 BL；需用户手动装并用无线调试启动 | ✅ 主通道（无 root 时的默认） |
| **REAREye（LSPosed）** | 唯一能解决**锁屏下直启** | ⭕ 可选，仅影响锁屏体验 |

**落地方式**：参照 MiRoot 的 `capability/PrivilegedShell.kt` + `ITaskService.aidl`，做一层统一特权执行入口：

- 首选 root：`ProcessBuilder("su", "-c", cmd)`
- 失败回退 Shizuku：Shizuku `UserService`（AIDL）执行
- 需要暴露的能力：
  - `executeShellCommand(cmd)` —— 跑 `am start --display 1`
  - `moveTaskToDisplay(taskId, displayId)` —— 占位迁屏
  - `getForegroundComponentOnDisplay(displayId)` —— 验证落屏
  - `disableSubScreenLauncher()` / `enableSubScreenLauncher()` —— 接管/恢复官方背屏中心

> ⚠️ Shizuku 的 `UserService` 需要在 manifest 声明并处理权限回调。MiRoot 用的是**用户级 Service + AIDL**，比 `Shizuku.newProcess` 反射稳定，建议照抄这个结构。

### 3.2 背屏内容承载：复用前端渲染 + 背屏专用布局 ✅已确认

| 方案 | 评价 |
|---|---|
| **A. 第二个 Activity + WebView，加载 Folia 的「背屏」路由** | ✅ **采用**：复用现有歌词渲染与 visualizer 效果；只写一套背屏专用布局 |
| B. 第二个 Activity + 原生 View 手写歌词 | ❌ 等于重写全部歌词效果，工作量与风格割裂都不可接受 |

**要点：**

- 在 `src/utils/appSurface.ts` 增加 `isRearLyricsSurface`（URL 参数 `?rear=1`），`bootstrap.tsx` 按它挂载新根组件 `RearLyricsApp`。
- 背屏 WebView 与主 WebView 加载**同一份 `dist`**，不需要单独打包。
- **不是**「只画歌词的静态页」：背屏同样复用 visualizer 的模式与歌词效果，只是布局和入口按背屏尺寸重排。
- 背屏提供**独立性能档位**（分辨率 / 帧率 / 是否启用重特效），用来平衡小屏发热；默认按机型给一个保守档。

> ❓**待定**：背屏是否默认跟随主屏的 visualizer 模式？建议「默认跟随，可单独覆盖」。

### 3.3 状态同步：本地事件流，双向

背屏需要拿到：当前歌曲、歌词行（含逐字时序）、播放进度、播放/暂停、封面、主题色、当前效果参数。
背屏需要回写：切歌指令、效果参数修改、歌词设置修改。

| 方案 | 评价 |
|---|---|
| **A. 本地 HTTP + SSE**（扩展 `LocalAudioServer`） | ✅ **主链路**：与 Folia 既有 OBS 链路同构，天然跨 WebView |
| B. Capacitor 插件桥 | ✅ **指令通道**：背屏的「切歌 / 改设置」等动作走插件回调主屏 |
| C. localStorage / BroadcastChannel | ⚠️ 同一 App 的多个 WebView 共享 DOM Storage，理论上可读；但 store 不会自动感知变化，不可作为主同步机制 |

**推荐组合：**

- **状态下发**：主屏 publisher → 原生缓存 → SSE 广播 → 背屏订阅（复用 OBS 的 `EventSource` 订阅写法）。
- **指令上行**：背屏 → Capacitor 插件 → 主屏执行（切歌、改设置、开关投屏）。
- **时钟**：SSE 带 `clock` 字段 + 前端本地外推（OBS 已这么做，250ms 一次即可）。

> ⚠️ **设计原则**：设置状态的**唯一真源仍在主屏**。背屏只发「修改指令」，由主屏写入并广播回来，避免两个 WebView 各写一份 localStorage 造成状态分叉。

### 3.4 左挖孔安全区与背景铺满

**硬件特征（已确认）**：左侧挖孔，**竖向排列的两个孔基本铺满整个左侧区域**，那里只有一点点显示，所以**左侧整条竖带直接不用**。

**结论：不做精细 cutout 适配。** 直接用一条**固定宽度的左侧安全带**即可，不需要解析 cutout、不需要多矩形并集。

**背景层**：铺满整个背屏，允许轻微越界（超出部分被裁掉）；背景层不受安全带约束。

**内容层（当前实现：画布右缘外扩，把渲染中心顶到可见区中心）**：
- 左侧安全带宽度取**固定常量 `296px`**（本机实测值，@450dpi 约合 105.2 CSS px）。MiRoot 的 277px 偏小 19px，本项目用实测值。
- 背屏 Activity 设置 `layoutInDisplayCutoutMode = LAYOUT_IN_DISPLAY_CUTOUT_MODE_ALWAYS`（或 `SHORT_EDGES`），让背景能延伸到挖孔区。
- **画布不窄反宽**：歌词层仍从 `left: 0` 起，但右缘外扩 `safeLeftCss` ⇒ 宽度 ≈ `347 + 106 = 453`
  （347 视口下实际写 `right: -106px`），多出来的 106px 落在屏幕外，被舞台的 `overflow-hidden` 裁掉。
  于是画布**铺满整屏、左侧一条缝都没有**，而画布自身的中心 = `(347 + 106) / 2 ≈ 226.5`，
  正好等于可见区中心 `safeLeftCss + 可见宽 / 2`。
- **所有「按自身宽度居中 / 按自身宽度排版」的内容自动归位**：各 visualizer 的居中容器、字幕层的
  `left-0 right-0 text-center` 一行代码都不用改，居中基准自动变成右侧可见区。
- 各 visualizer 的换行宽度 / 字号 `clamp` 随之按 453 计算（比整屏还略宽），
  所以**歌词不会被避让压小**，剩下的字号问题只来自模式自带的排版下限（§13.12）。
- 越出可见区、落在挖孔带里的内容属于非主视角内容，**接受**（主歌词行本身仍居中于可见区）；背景层不受约束。
  「绘光」这类自带取景框装饰的模式，装饰线会画进左侧竖带，属同一类可接受的越界。
- 安全带宽度做成**可配置项**（换机型或调留白都能改）。
- 已否掉的旧做法（都试过，别再回头）：
  ① 把歌词层收进 `left: safeLeftCss` 的右侧区域 —— 构图按 242px 宽重新排版、被压扁；
  ② 整块画布 `translateX(safeLeftCss / 2)` 右移 —— 左侧露出 53px 空白，看起来「没铺满、很生硬」；
  ③ 给绘制中心单独加偏移 —— 要逐个模式改渲染代码，等于把 14 个模式都改一遍。

> ⚠️ **字号**：背屏 CSS 视口只有 347×212，而各 visualizer 模式的主歌词字号都写成
> `clamp(Nrem, M vw, K rem)` —— 小视口下 clamp 取的是 rem 那个下限，**不会随屏幕缩小**，
> 于是 1.0 倍率下歌词常常撑出可见区。字号倍率的可设下限因此从 `0.85` 放宽到 `0.5`
> （`useTypographySettingsStore` 的 `LYRICS_FONT_SCALE_MIN`），默认值仍是 1。
>
> 放宽下限只解决了「能调小」，没解决「一块屏调小另一块也跟着变小」。所以背屏用的是**独立的一份
> 字号**（`rearLyricsFontScale`），主屏的 `lyricsFontScale` 不受影响，详见 §13.6。

**触摸层**：
- 左侧安全带内**不放置任何交互控件**，并对该区域加 `pointer-events: none`。
- 两个孔是物理挖孔，孔本身没有屏幕，触摸事件自然不会产生；但**竖带里非孔的部分是屏**，必须靠布局约束保证没有控件落在那里。
- 所有可点元素（控制面板、按钮）都在安全带右侧。

> ⚠️ 安全带宽度在 CSS 里是逻辑像素，和原生 px 不是一回事。建议由原生算好后**注入 WebView**（CSS 变量或 URL 参数），避免单位换算踩坑。

### 3.5 背屏交互 ✅已确认

背屏支持触摸（左侧竖带除外），所以切歌与设置都可以在背屏完成：

| 交互 | 方案 |
|---|---|

### 3.6 背屏 UI 设计

背屏为横向区域（宽 > 高，宽高比约 1.53–1.64），左侧竖排双孔。分两层：

**层一：歌词态（默认常驻）**

```
┌───────────────────────────────────────────────┐
│ ┃●┃ │                                        │
│ ┃●┃ │        主歌词（大字，逐字高亮）          │
│ 左侧│                                        │
│ 安全│        译文 / 下一句（小字）             │
│ 竖带│  ─────────────────────────────         │
│     │  歌名 · 歌手            ▁▂▃▅▇ 进度      │
└───────────────────────────────────────────────┘
   ↑ 只铺背景、不可触摸    ↑ 构图中心对齐这一块的中心
```

- 左侧竖带 = 两个孔的外接宽度，**只铺背景**：不放可读内容、不放触摸目标。
- 可见区 = 安全区右缘到屏幕右缘；画布仍是整屏，只把**渲染中心**右移 `safeLeftCss / 2`（`viewportInsetLeft` → `stageViewport.offsetX`）。

- 底部一条极细进度线 + 歌名歌手，默认低存在感。

**层二：控制面板（轻触/上滑唤起，覆盖下半屏）**

```
┌───────────────────────────────────────────────┐
│ ┃●┃ │  歌词（大）                            │
│ 竖带│                                        │
├─────┴─────────────────────────────────────────┤
│  [队列] [效果] [歌词]              ✕          │  ← 三个页签
│  ─────────────────────────────────────────    │
│   （当前页签内容，复用主屏组件的紧凑版）        │
└───────────────────────────────────────────────┘
   ↑ 面板左边缘也不得伸进竖带
```

- **队列**：上一首 / 播放暂停 / 下一首 + 可滚动队列。
- **效果**：visualizer 模式选择 + 该模式调参。
- **歌词**：字号、字体、颜色、译文、逐字高亮、时间轴偏移——现有歌词设置弹窗的压缩版。

**组件复用原则**：不复制逻辑，只做「紧凑外壳 + 复用内部控件」。新增外壳放 `src/components/rear/*`，内部仍调用现有的设置控件与 store。

### 4.1 实际实现的架构（阶段 2/3 落地版）

上面 §4 是最初的规划图；真正跑起来的是下面这张。差别只有一处：**没有本地 HTTP / SSE**，
两个 WebView 之间的数据全部走 Capacitor 插件事件 + `evaluateJavascript`。

```
┌──────────────────────────── 主屏 WebView（?rear 为空）────────────────────────────┐
│  App.tsx                                                                          │
│   ├─ useRearLyricsTransport()   ── 听 rearState，提供 transport 给发布器            │
│   ├─ useRearLyricsHostActions() ── 听 command，落到 next/prev/seek/mode/字号       │
│   ├─ useObsBrowserSourcePublisher({ transport, isRearLyricsActive })               │
│   │      └─ 同一份 config / clock / audio，多推一路给背屏                          │
│   └─ 设置 → 连接 → 背屏歌词卡片（RearLyricsSetting） / 命令面板 3 条命令            │
│                        │ RearProjection.publishSnapshot(kind, json)               │
└────────────────────────┼──────────────────────────────────────────────────────────┘
                         ▼
┌─────────────────── 原生（top.izuna.foliamajor.rear）──────────────────────────────┐
│  RearProjectionPlugin   getStatus / startProjection / stopProjection /            │
│                         requestPrivilege / openShizukuSettings / publishSnapshot  │
│  RearProjectionController  root 优先 → Shizuku 回退；直启优先 → 占位迁屏回退       │
│  RearLyricsChannel         缓存最近 config/clock/audio；ready() 时补推；转发指令   │
│  RearLyricsActivity        背屏 Activity（display 1）：WebView + 左侧 296px 吞触摸 │
│  RearLyricsHost            @JavascriptInterface：ready / requestSnapshot /        │
│                            send / log                                             │
└────────────────────────┬──────────────────────────────────────────────────────────┘
                         │ evaluateJavascript → window.__foliaRear.push(kind, json)
                         ▼
┌──────────────────────────── 背屏 WebView（?rear=1）──────────────────────────────┐
│  RearLyricsApp                                                                    │
│   ├─ 背景层：铺满整屏（含左侧安全带）                                              │
│   ├─ 歌词层：整屏（不收窄）+ viewportInsetLeft = safeLeftCss（实测 105 CSS px）    │
│   │          画布平移 safeLeftCss/2 → 渲染中心落在可见区中心                       │
│   ├─ RemotePlaybackStage + usePublishedPlaybackSource（与 OBS 源共用）             │
│   └─ RearLyricsControls：切歌 / 暂停 / 模式名 / 效果设置 / 退出（6 秒自动隐藏）      │
│                         │ window.FoliaRear.send(json)                             │
└─────────────────────────┼─────────────────────────────────────────────────────────┘
                          └─→ RearLyricsChannel.handleCommandFromRear → command 事件 → 主屏
```

**三条通道，一句话各自是什么：**

| 通道 | 方向 | 载体 | 用途 |
|---|---|---|---|
| `publishSnapshot` | 主屏 → 背屏 | Capacitor 插件方法 + `evaluateJavascript` | config / clock / audio 三份快照 |
| `rearState` | 原生 → 主屏 | Capacitor 事件（`retainUntilConsumed`） | 背屏页是否已就绪，决定发布器要不要推 |
| `command` | 背屏 → 主屏 | `@JavascriptInterface` + Capacitor 事件 | 切歌 / 暂停 / seek / 换模式 / 改字号 / 退出 |

**关键设计（为什么这么做）：**

1. **主屏是唯一真源。** 背屏不维护任何播放状态，所有操作都是「发意图 → 主屏改 store → 推回背屏」。
   这样不会出现「背屏改了、主屏没改」的分叉。
2. **载荷与 OBS 源同构。** `ObsBrowserSourcePublishTransport` 被抽出来当接口，
   背屏传输层和 Electron/OBS 传输层实现同一个接口，发布器只认接口。
   背屏因此直接复用 `VisualizerRenderer` 与 OBS 的时钟外推逻辑，不需要第二套渲染。
3. **`?rear=1` 是同源页面。** 背屏 Activity 用 `WebViewAssetLoader` 把 `https://localhost`
   映射到 `assets/public`，和主界面同源 → 共用同一份 `localStorage`，主题 / 字体 / 效果设置天然一致。
4. **左侧安全带是固定值。** `SAFE_LEFT_PX = 296`（物理像素），页面按
   `safeLeftPx × CSS 视口宽 ÷ 屏幕物理宽` 换算成 CSS px。它传给 `RemotePlaybackStage`
   的 `viewportInsetLeft`，由舞台把整块画布平移半个宽度（= 渲染中心右移到可见区中心）；
   画布本身不收窄，背景层不跟着平移，仍然铺满。

## 9. 附：MiRoot 移植实施细节（可直接照搬）

> 这一节是把 MiRoot 里真正跑通的实现细节提取出来，供 Folia 移植时直接对照。
> 路径统一相对 `F:\Android\App\MiRoot`。

### 9.1 Shizuku 依赖

MiRoot 用的是 **Shizuku 13.1.5**（`gradle/libs.versions.toml`）：

```toml
shizuku = "13.1.5"
shizuku-api      = { group = "dev.rikka.shizuku", name = "api",      version.ref = "shizuku" }
shizuku-provider = { group = "dev.rikka.shizuku", name = "provider", version.ref = "shizuku" }
```

```kotlin
implementation(libs.shizuku.api)
implementation(libs.shizuku.provider)
```

Folia 侧对应要加：`dev.rikka.shizuku:api`、`dev.rikka.shizuku:provider`，并在 manifest 声明 provider。

### 9.2 Manifest 声明模板

**应用级**（`AndroidManifest.xml` 的 `<application>` 内）：

```xml
<meta-data android:name="miui.rear.policy" android:value="1"/>
```

**背屏 Activity 级**（照搬 `RearScreenLyricsActivity` 的写法）：

```xml
<activity
    android:name=".rear.RearLyricsActivity"
    android:exported="true"
    android:excludeFromRecents="true"
    android:launchMode="singleInstance"
    android:taskAffinity="top.izuna.foliamajor.rear.lyrics"
    android:theme="@style/Theme.MiRoot.Transparent"
    android:configChanges="orientation|screenSize|keyboardHidden|screenLayout|uiMode|smallestScreenSize|density"
    android:showWhenLocked="true"
    android:enableOnBackInvokedCallback="false">
    <meta-data android:name="miui.rear.policy" android:value="miui"/>
</activity>
```

要点：**独立 taskAffinity**（避免和 `MainActivity` 同任务栈被一起拉走）、`singleInstance`、完整 `configChanges`（含 `density`）。

### 9.3 启动命令模板

```java
String component = getPackageName() + "/" + RearLyricsActivity.class.getName();

// 主屏占位（必须显式 --display 0，否则会被 miui.rear.policy 路由到背屏而 abort）
String mainCmd = "am start --display 0 -n " + component;

// 背屏直启
String directCmd = "am start --display 1 -n " + component;
```

启动后轮询 `am stack list`，确认该 Activity 已出现在 `displayId=1` 的 RootTask 段内（MiRoot 用 `StackListSnapshot` 做单次 dump + 内存搜索，避免反复起子进程）。

### 9.4 迁屏命令（三级回退）

MiRoot 的 `TaskService.moveTaskToDisplay()` 按顺序试三种写法。**小米 17 Pro Max / Android 17 实测结果**：

| 写法 | Android 17 实测 |
|---|---|
| `am task move-task-to-display <taskId> <displayId>` | ❌ `Error: unknown command 'move-task-to-display'` |
| `am display move-stack <taskId> <displayId>` | ✅ 可用（本机唯一有效的迁屏命令） |
| `service call activity_task 50 i32 <taskId> i32 <displayId>` | ❌ 事务号已变（50 现在是 `moveRootTaskToTaskDisplayArea`），只在老 ROM 上有意义 |

```java
// 实际保留的三级回退（按顺序试，每一步都用 am stack list 复核效果）
"am task move-task-to-display " + taskId + " " + displayId   // 老 ROM
"am display move-stack " + taskId + " " + displayId          // Android 17 可用
"service call activity_task 50 i32 " + taskId + " i32 " + displayId  // 更老的 ROM
```

**关闭背屏页**：Android 17 上 `am task remove` 同样不存在（`am task` 只剩 lock/resize/focus），要用
`am stack remove <RootTaskId>`；拿不到时兜底让背屏页自己 `finish()`（`--es folia.rear.cmd finish`）。

### 9.5 背屏信息获取（分辨率 / DPI / Cutout）

MiRoot 不靠 Android API，而是**解析 `dumpsys display`**（`lyrics/RearDisplayHelper.java`）：

- 分辨率：正则 `displayId=1[^}]*deviceWidth=(\d+),\s*deviceHeight=(\d+)`
- DPI：在 Display 1 的 `DisplayDeviceInfo` 区块里匹配 `density\s+(\d+)`
- Cutout：匹配 `DisplayCutout{insets=Rect(left, top - right, bottom)}`（注意系统 dump 用的是短横线分隔）

结果缓存到 `DisplayInfoCache`（单例，启动时初始化一次），取不到时的默认值是 `904×572 / dpi 450 / cutout 空`。

> ℹ️ **对本项目的意义**：本项目**不需要**这套精细解析——两个孔基本铺满左侧，直接用一条固定宽度的左侧安全带即可（见 3.4）。MiRoot 这套 `dumpsys display` 解析仍值得保留，用于**取背屏分辨率与 DPI**（WebView 布局、字号换算要用）。

### 9.6 禁用 / 恢复官方背屏中心

**投屏时**：`force-stop` / `pm disable` `com.xiaomi.subscreencenter`（MiRoot 用引用计数 `OfficialSubscreenMiRootProjectionSession`，保证多个界面共享时不会互相踩）。

**退出时恢复**：

### 12.1 仓库缺文件（`.gitignore` 误伤，必须先修）

根 `.gitignore` 里的 `build/` 规则会匹配**任意层级**名为 `build` 的目录，于是：

| 缺失路径 | 后果 | 处理 |
|---|---|---|
| `dev/build/buildIdentity.mjs` | `vite.config.ts` 顶部 import 失败，前端构建直接报错 | 补了一个最小实现（导出 `resolveBuildRepo` / `normalizeBuildCommit`） |
| `build/icon.png` | `UserGuidePageContent.tsx` import 失败 | 用 `android/img/icon.png` 复制补齐 |
| `build/miao.png` | `SettingsModal.tsx` import 失败（设置里的喵彩蛋图） | **临时占位图**，建议从上游仓库补回真图 |

同时给 `.gitignore` 加了 `!dev/build/` / `!dev/build/**` 反排除，避免再次丢文件。

> ⚠️ 你的仓库副本还缺 `build/trayTemplate.png`、`build/thumbar/*.png`、`build/fetchModels.mjs` 等
> （只在 Electron 桌面版打包时用，安卓链路不受影响）。建议之后从 GitHub 重新克隆一份完整仓库。

### 12.2 `npx cap sync` 与 TypeScript 7 不兼容

项目用 `typescript ~7.0.2`，而 Capacitor CLI 8.4.2 的 `capacitor.config.ts` 解析器访问
`ts.ModuleKind`，在 TS 7 下是 `undefined`，报 `Cannot read properties of undefined (reading 'CommonJS')`。

**临时绕法**：同步前把 `capacitor.config.ts` 改名为 `capacitor.config.ts.disabled`，
让 CLI 回落到等价的 `capacitor.config.json`，同步完再改回来。

### 12.3 背屏页一启动就崩：decorView 还没创建

`onCreate` 里直接调 `window.getInsetsController()` → `PhoneWindow.getInsetsController()` →
`DecorView.getWindowInsetsController()` on null → NPE 崩溃。
**修复**：先 `window.getDecorView()` 触发 decor 创建，再取 insets controller；并在 `onWindowFocusChanged`
里重新收一次系统栏（背屏焦点会被官方背屏中心抢）。

### 12.4 Shizuku 通道下 `Process.exitValue()` 会抛异常（最容易踩的坑）

现象：投屏其实成功了，但 App 进程**崩溃重启**，日志里是
`java.lang.IllegalArgumentException: process hasn't exited`。

根因：`ShizukuRemoteProcess.exitValue()` 会走 binder 到远端，远端在进程未退出时抛
`IllegalArgumentException`；`Process.isAlive()` 只吞 `IllegalThreadStateException`，所以异常逃逸，
而它出现在 `finally` 块里 → 直接冒泡成未捕获异常。

**修复**（`PrivilegedShell`）：

1. 清理子进程不再判断 `isAlive()`，直接 `destroyForcibly()` 并吞掉一切异常。
2. 执行命令不再依赖退出码：`run()` 读到 stdout EOF 即视为命令结束；`capture()` 直接把读到的内容当结果。
3. 命令成败一律**按效果复核**（再抓一次 `am stack list`），并且复核要**轮询退避**
   （12 × 60ms），因为系统把任务变更写进栈快照有延迟，命令刚返回就复核会误判。

### 12.5 `am start` 不带 `--display` 会把界面丢到背屏

调试时执行 `adb shell am start -n top.izuna.foliamajor/.MainActivity`，主界面会落到 display 1
（因为 shell 当时所在的 display 是背屏）。**排查背屏问题时，主界面一定要写死 `--display 0`。**
投屏代码里 `directLaunchCmd` / `placeholderLaunchCmd` 都显式带 `--display`，不受影响。

### 12.6 其它实测结论

- 背屏页用 `layoutInDisplayCutoutMode = ALWAYS` + 黑底，背景能铺满整块屏；左侧 296px 竖带用原生
  `View`（clickable）盖在 WebView 上吞触摸，比只靠 CSS `pointer-events:none` 更稳。
- WebView 视口用 `width=device-width, initial-scale=1, viewport-fit=cover`，实测 CSS 视口
  **347 × 212**、密度 2.8125，于是 296px 安全带 = **105 CSS px**（页面里用 `devicePixelRatio` 换算，
  不写死）。
- 背屏可触摸（除左侧竖带）：实测用 `input -d 1 tap` 点背屏右上角 ✕ 能关闭背屏页。
- 退出投屏**不需要**强行拉起官方背屏中心：任务被移除后，系统会自动把背屏原先显示的内容还回来。
  因此 `stop()` 里没有 `pm disable/enable com.xiaomi.subscreencenter`。
- Shizuku 授权：`RearProjection.requestPrivilege()` 会拉起 Shizuku 的授权弹窗（`始终允许`）；
  授权后 `getStatus()` 返回 `channel: "shizuku"`。debug 包与 release 包签名不同，换签名要重新授权。

### 12.9 APK 里绝对不能带 Service Worker（升级后界面不更新的元凶）

**症状**：明明 `install -r` 装上了新包、进程也重启了，界面却还是旧的；`adb pull` 出来的
`dist/assets/main-*.js` 哈希和 WebView 实际加载的哈希对不上。

**原因**：`vite.config.ts` 里的 `vite-plugin-pwa` 默认对**所有**构建生效，于是 APK 里也打进了一份
`sw.js` + `registerSW.js`。Service Worker 把 `index.html` 和整包 JS 预缓存到
`app_webview/Default/Service Worker/CacheStorage`，导航请求由它直接从 precache 返回 ——
新包虽然已经落盘，首屏拿到的还是旧缓存。APK 的资源本来就随包发布，SW 一点价值都没有，只有这个副作用。

**修复（两层）**：

1. `vite.config.ts` 里 `isCapacitorBuild`（`FOLIA_BUILD_TARGET === 'capacitor'`）时**不注册** `VitePWA`，
   APK 里不再有 `sw.js` / `registerSW.js` / `manifest.webmanifest`。
2. 老安装的设备上注册还在，所以新增 `WebViewCacheReset`：每次安装后的第一次启动，
   删掉 `app_webview/Default/Service Worker`（只删它，**不碰** `IndexedDB` / `Local Storage`，
   曲库索引和设置都在那里）。靠 `PackageInfo.lastUpdateTime` 做闸门，一次安装只跑一次，
   并且必须在 Activity 的 `super.onCreate` 之前调用 —— 那一步就会创建 WebView。

> 判定方法：在页面里跑 `navigator.serviceWorker.getRegistrations()`。
> 正常应该返回空数组；返回 `https://localhost/sw.js` 就说明吃到了旧缓存。
> 想临时救急，用 CDP 执行 `location.reload()` 也能刷到新资源（SW 会在这次加载里自我更新）。

### 12.10 背屏页加载失败：`/publicindex.html`（被 SW 缓存掩盖的老 bug）

`WebViewAssetLoader` 的 path handler 拿到的是 **去掉前缀后** 的路径，形态随 androidx 版本变化
（可能带前导 `/`，也可能不带）。原来的实现直接 `handle("/public" + path)`，遇到不带前导斜杠的
情况会拼出 `/publicindex.html`，导航直接变成 Chromium 的 net error 页（就是那块黑色 + 绿色小机器人）。

它之所以一直没被发现，是因为当时页面导航被 Service Worker 的 precache 接走了（见 §12.9）——
SW 一停用、缓存一清，这个 bug 立刻暴露。修法：拼之前先把路径归一化成以 `/` 开头。

### 12.11 官方背屏中心会抢走 display 1（黑屏的另一个原因）

**症状**：背屏歌词先正常显示，过一会儿（主屏切应用 / 背屏闲置之后）整块变黑，界面没了。

**实测**：`dumpsys activity activities` 里 display 1 的 top 变成
`com.xiaomi.subscreencenter/.SubScreenLauncher`，我们的任务还在但 `visible=false`、
`mLastPausedActivity=RearLyricsActivity` —— 任务没死，是被盖住了。

**处理（对齐 MiRoot）**：

1. 落屏成功后 `pm disable-user --user 0 com.xiaomi.subscreencenter` + `am force-stop`，
   退出投屏时 `pm enable` 并把它重新拉回背屏（`RearProjectionController` 的 start/stop）。
   划掉任务不走 stop() 时，`RearLyricsActivity.onDestroy` 也会兜底恢复。
2. 压掉官方中心之后**再 start 一次我们的页面**：MIUI 可能在禁用它的同时把背屏熄掉，
   重新 start 配合 Activity 的 `android:turnScreenOn="true"` 能把背屏点回来。

> ⚠️ 待真机复核：背屏闲置几分钟后会 `isSleeping=true`（背屏整块变黑但任务还在）。
> 目前靠 `turnScreenOn` 兜底，阶段 4 的「投屏常亮」还需要补（主动唤醒 / 保持屏幕常亮）。
> 如果背屏一直黑着，先在主屏「设置 → 连接 → 背屏歌词 → 退出背屏歌词」跑一次恢复，
> 或者直接 `adb shell pm enable com.xiaomi.subscreencenter`。

### 13.3 背屏布局与触摸

- **背景层**：`inset: 0` 铺满整块屏，包括左侧安全带。
- **歌词层**：`left: 0` + 右缘外扩 `safeLeftCss`（渲染成 `right: -106px`，347 CSS 视口下总宽 ≈ 453，
  超出屏幕的 106px 被 `overflow-hidden` 裁掉 → 视觉上仍然铺满整屏），把
  `viewportInsetLeft = safeLeftCss`（347 CSS 视口下 = 105px）交给 `RemotePlaybackStage`；
  画布中心因此落在 `226.5`，正好是可见区中心，各 visualizer 与字幕层里「按自身宽度居中」的内容
  **自动归位**，不需要逐个模式改渲染代码。偏移量另外通过 `stageViewport` 的 `offsetX` 发布
  （`RemotePlaybackStage` 发布的仍是整屏宽高），供需要自己摆位的渲染层使用。
- **实测（本地探针，2026-10-14）**：`classic` / `still` / `cappella` / `pendolo` / `monet` / `tilt` /
  `diorama` / `fume` / `lumiere` / `tempera` 的主歌词行水平中心 ≈ **226.5**，
  可见区中心 = 105 + (347 − 105) / 2 = **226**，误差 < 1px。
- **实测（真机，2026-10-15，小米 17 Pro Max）**：背屏页面 `innerWidth=347 / innerHeight=212 / dpr=2.8125`；
  画布宿主 `left: 0 / width: 453 / style="right: -106px"`，和本地探针完全一致；播放中主歌词
  （`lumiere` 模式）落在右侧可见区，左侧无空白缝。「绘光」自带的取景框装饰会画进左侧竖带，
  那是模式自己的装饰，不是布局问题。
- **字号**：背屏用的是**独立的一份字号**（`rearLyricsFontScale`，§13.6），调它不影响主屏；
  背屏面板「通用」页签的预设从 **100%** 起步（100 / 110 / 125 / 140%），
  而且**不会因为避开摄像头被压小**（画布是整屏）。滑杆下限仍是 `REAR_LYRICS_FONT_SCALE_MIN`（0.5），
  只作为极端情况的手动微调；部分模式在低倍率下仍会溢出（§13.12），一般不建议往小调。
- **触控层**：控制条与设置面板同样从 `safeLeftCss` 开始，不会落进摄像头竖带。
  这一层取 `z-50`（高于舞台内部的 z 层级），否则会被舞台里逃逸出来的 `z-20` 歌词行盖住（§13.11）。
- **竖带不可触摸**：由原生 `RearLyricsActivity` 里一个 296px 宽的透明 `View` 吞掉，比只靠 CSS 稳。

覆盖成要展示的状态 —— 它验的是卡片的**视觉**，不是插件链路（插件链路只能在真机上验）。

### 13.6 背屏字号独立于主屏（`rearLyricsFontScale`）

**问题**：背屏只有 347×212 CSS px，主屏 1200×2608。两代背屏和主屏共用同一份字号必然一头不合适：
按主屏调到舒服的值，背屏就撑出可见区；按背屏调小，主屏又太小。早先的做法是两边共用
`lyricsFontScale`，在背屏上改字号会**覆盖主屏的设置**。

**结论**：加一份**只给背屏用**的字号，两份互不影响。

数据流（仍然是「主屏是唯一真源」）：

```
主屏设置卡片滑块 ─┐
                  ├─→ useTypographySettingsStore.rearLyricsFontScale
背屏控制面板 +/- ──┘     （localStorage: rear_lyrics_font_scale，范围 1~1.4）
                                  │
                                  ▼
            useObsBrowserSourcePublisher 把 config 推给背屏
            （config 里同时带 lyricsFontScale 和 rearLyricsFontScale）
                                  │
                                  ▼
      RearLyricsApp 渲染前把 lyricsFontScale 覆盖成 rearLyricsFontScale
            （只改这一个字段；主题 / 背景 / 模式 / 歌词仍然共用同一份 config）
```

要点：

- **不是两条 config**：发布器仍然只构建一份 config，只是多带一个字段，覆盖动作放在背屏页渲染前。
  OBS 通道拿到的仍是主屏字号，两条通道的构建逻辑不会分叉。
- **背屏只发意图**：背屏控制面板的 `+ / -` 发 `setLyricsFontScale` 指令，主屏 `useRearLyricsHostActions`
  收到后写的是 `handleSetRearLyricsFontScale`（不是 `handleSetLyricsFontScale`）。
- **进外观配置导入导出**：它是「字号」，所以跟着 shortcode / JSON 走（`rlf` 短码 + `validKeys` 白名单
  + 导入分组 `fonts`），换机器恢复观感时不会丢。
- **默认值 1**，和主屏默认一致；从没设置过时，背屏显示与主屏字号相同。
- **下限就是 1**：`REAR_LYRICS_FONT_SCALE_MIN = 1`，背屏面板与主屏卡片上的背屏滑杆都从 100% 起步，
  不能再往小调（用户口径：「背屏歌词大小不能再调小」）。主屏自己的 `LYRICS_FONT_SCALE_MIN = 0.5` 不变。

**真机验证（2026-10-14，Xiaomi 17 Pro Max）**：

| 操作 | 结果 |
|---|---|
| 主屏 `lyrics_font_scale` = 0.75，背屏从未设置过 | 背屏面板显示 1.00（背屏自己的默认值），主屏字号没有传导过去 |
| 背屏面板点 4 次「−」 | 背屏面板 1.00 → 0.80；`localStorage.rear_lyrics_font_scale` = `0.8`，`lyrics_font_scale` 仍是 `0.75` |
| 主屏设置卡片滑块拖到 0.90 | `rear_lyrics_font_scale` = `0.9`，背屏面板随即显示 0.90 |

截图：`_shots/rear_fontscale_090.png`（背屏面板显示 0.90）、`_shots/rear_lyrics_090.png`（0.90 下的歌词）。

### 13.8 背屏设置面板（= 主屏同款外壳 + 条目逐条照搬 + 背屏专用项）

**形态**：背屏底部**上滑**或点控制栏的齿轮唤出；面板本身**只覆盖可见区**（`left: safeLeftCss`，
即 347 CSS 视口下从 105px 到右边缘，实际宽 242px），不会压进左侧摄像头竖带。

面板的口径是「**和主屏一样**」，不是「风格相似」——用户反复强调过这一点，落地成四条硬要求：

1. **外壳同款**：`bg-black/40`（日间 `bg-white/60`）+ `backdrop-blur-3xl` + `rounded-3xl` + `shadow-2xl`，
   与主屏播放页那个面板（`UnifiedPanel` 的 `glassBg`）同值；顶部页签条也是那一条分段式图标页签
   （`bg-white/5 p-1 rounded-xl` 容器、选中格 `bg-white/10 shadow-sm`、未选中只降 `opacity-40`、图标 16px），
   见 `src/components/rear/rearPanelStyle.ts` 的 `resolveRearPanelChrome`。
2. **条目照搬**：每个页签的内容对着主屏 `src/components/visualizer/VisPlaygroundSettingsPanel.tsx`
   逐条搬过来，顺序、分组、卡头（标题 + 说明 + 右上「默认」）、控件形态都不变。
3. **控件同一份实现**：`src/components/settingsRows/settingsRowKit.tsx` 里的
   `SettingsSectionCard / SettingsPresetGroup / SettingsToggleRow / SettingsSliderRow / SettingsResetButton`
   带一个 `density` 档位参数。

- `density="main"`：数值逐条对齐主屏原 `VisPlaygroundSettingsPanel`，接过去渲染结果不变。
- `density="rear"`：**背屏档现在与主屏同尺寸**（`REAR_TUNING_PANEL_SCALE = 1`），颜色、结构、
  选中态算法本来就共用，所以两边控件是逐像素一致的。

两处集中的例外（写在 `resolveDensityTint` / `resolveUnselectedOptionStyle` / `resolveTabsContainerBg`）：
背屏面板底色与「未选中项 / 页签容器」底色若同色会看不见，所以背屏档改用卡片底色 / 次要色薄涂。

背屏专属项（主屏没有、只在背屏有意义的设置）单独收进「背屏专用」卡片，和「主屏同款」一眼分开，
以后新增背屏专属项也往那张卡里放。

**刻意没搬的两条**（背屏上放了没意义，其余一律照搬）：

- 「预览文本」预设组：那一组选的是主屏预览画面里唱哪段占位歌词，而背屏放的是正在播的真实歌词，
  搬过来会变成一个按了没反应的按钮。
- 字体样式里的「自定义字体」入口（通用页与字幕页都有）：那要开字体选择器，背屏这块小屏放不下。

| 页签 | 内容（对照主屏对应页签） |
|---|---|
| 歌词 | **背屏特有页**：歌名 / 歌手 · 专辑 + 可滚动歌词列表（点行 seek）。**无封面** |
| 列表 | **背屏特有页**：播放队列（对照主屏播放页的「列表」页 / `panelTab/QueueTab.tsx`）。表头「播放队列 (n)」+ 打乱按钮，行 = 高亮竖条 + 歌名（含「不可用」标签）+ 歌手 + 三个常显按钮（下一首播 / 移到末尾 / 移除）；当前行 `bg-white/15` 并自动滚到中间。去掉封面、去掉拖拽排序（小屏拖不准），**操作按下标回主屏执行** |
| 控制 | 主屏播放页「控制」页的背屏版：循环模式 / 喜爱 / 智能过渡 + 音量条（只用背屏放得下的那几项） |
| 通用 | 主屏「通用」全量：卡头 + 「默认」、字体（Sans/Serif/Mono）、字号预设 + 滑杆（写 `rearLyricsFontScale`，**背屏专用字段**，预设从 100% 起）、自动字号提示框、字重（自动开关 + Thin/Regular/Bold 预设 + 100–900 滑杆）、整体透明度；下挂「背屏专用」卡：**「播放即自动背屏显示」开关** |
| 效果 | 主屏「背景」与「动画」两页**拼成一页**（用户要求「一页设两个效果」）：背景卡（原生毛玻璃提示条 + 取景器行 + 各背景模式调参，背屏**不含 url** 上传项）+ 歌词卡（歌词渲染器 + 取景器行 + 各模式调参）+ 各自缺失模组说明 + `FoliumTuningCards`（模组注册的调参卡）。两行都是主屏同款 `ModeStepperRow`（`‹ 字形 模式名 ›`，点中间展开完整下拉），「默认」沿用背屏卡片右上角那颗 |
| 字幕 | 主屏「字幕」全量：卡 1（卡头 + 「默认」+ 隐藏底部字幕 + 内容模式 + 背景开关 + 模糊开关 + 继承歌词字体 + 字号 + 字重 + 透明度）+ 卡 2（和声字幕两开关） |

「列表」页与另外五页的写通道不同：它是**唯一按下标回主屏执行**的页 —— 队列随 config 只读下行
（`config.queue` / `config.queueIndex`，由 `useObsBrowserSourcePublisher` 从 `usePlaybackStore.playQueue`
构建），背屏点一行只发指令、不本地改队列：

| 背屏动作 | 指令 | 主屏落点 |
|---|---|---|
| 点某一行 | `playQueueIndex` | `playSong(playQueue[index], playQueue, false, { shouldNavigateToPlayer: false })` |
| 下一首播 | `moveQueueSongToNext` | `createQueueMutations` 的 `moveQueueSongToNext(index)` |
| 移到末尾 | `moveQueueSongToEnd` | `createQueueMutations` 的 `moveQueueSongToEnd(index)` |
| 移除 | `removeQueueSong` | `createQueueMutations` 的 `removeQueueSong(index)` |
| 打乱 | `shuffleQueue` | `usePlaybackQueueController` 的 `shuffleQueue()` |

四个带下标的指令都过 `Number.isInteger(command.index)` 校验再执行，越界直接丢弃。

**写协议（关键）**：背屏面板**不持有任何可写业务状态**。所有改动都补丁成一条
`applySettings` 指令发回主屏，主屏 store 改完再推回来：

```
背屏控件 ──→ onSettings(patch)
        └─→ sendRearLyricsCommand({ type: 'applySettings', patch })
                              │
                              ▼
        主屏 App.tsx 的 applySettings 分支写进对应 store
                              │
                              ▼
        useObsBrowserSourcePublisher 重新推 config → 背屏重渲染
```

好处：背屏和主屏**永远不会各存一份状态**；面板代码只是「一屏控件 + 一个 patch 出口」，
不需要为背屏再写一套 store。注册表自带的调参面板（背景/动画页签）也是走同一个出口，
`tuningPatch` / `resetTuning` 都在 `RearLyricsSettingsPatch` 里。

**效果页那条「更多设置」的去向**：主屏取景器行右侧的「更多设置」会跳到主屏的设置页；背屏没有独立设置页，
模式自己的调参卡就在同一页下方，所以那颗按钮改成把对应调参卡 `scrollIntoView` 滚进视野
（按钮位置与款式不变，行为换成背屏能做到的等价动作）。调参卡外层带 `data-rear-tuning="background|visualizer"` 锚点。

### 13.11 背屏面板盖不住歌词：层叠上下文坑（已修）

**现象**：面板已经改成接近不透明（0.96 / 0.98），滑杆上还是能看到大号歌词透出来压在控件上，
而且字是**实的**、不是淡的 —— 说明不是透明度问题。

**根因**：`RearLyricsApp` 的歌词层是 `absolute inset-0`（`z-index: auto`），**不构成层叠上下文**，
于是舞台内部的 `z-10 / z-20 / z-30`（歌词行、字幕、和声）会**逃逸到根层叠上下文**，
和手势层（原来 `z-10`）同场比较 —— `20 > 10`，歌词就画到面板上面去了。
（面板虽然在手势层里是 `z-30`，但它被手势层这个层叠上下文关在里面，出不来。）

**修法**：把手势层（控制栏 + 面板的父节点）提到 `z-50`，高于舞台当前用到的最高层级 30。
**没有**给歌词层加 `isolation: isolate`：那会把 `mix-blend-mode`（`VisualizerStill` 的
暗角叠加等）隔离在歌词层内部，改变与背景层的混合效果，属于看不见的视觉回归。

**验证**：改成 `z-50` 后重拍 `_shots/panel-lyrics.png` 等五张，
面板内部完全盖住歌词，滑杆、胶囊、列表都清晰（见 §13.8 的探针命令）。

### 13.12 已知：部分模式在最小字号下仍会溢出（不要再降字号）

背屏视口只有 347×212，部分歌词模式自带的排版下限（`clamp()` 里的 `rem` 下限、
硬编码的最小字号）比最小倍率算出来的还大，所以这几个模式在最小字号下仍会溢出可见区
（背屏最小倍率现为 1；画布已外扩，所以这里只说模式自身的下限）：

| 溢出模式 | 说明 |
|---|---|
| `classic` | 主歌词自带最小字号，已超出背屏可见区 |
| `monet` | 轨道式排版有固定行高/字号下限 |
| `partita` | 分栏排版有固定字号下限 |
| `pendolo` | 钟摆构图按固定尺寸布局 |
| `still` | 静止构图按固定字号排 |

**结论：不要为了这几个模式继续下调字号下限。** 背屏下限已是 1（用户明确要求「不能再调小」）；
现在画布外侧还有 106px 余量，越界一点也只是顶到挖孔带，比压字号更不伤观感。
背屏上遇到这几个模式，换一个模式（或接受轻微越界）比继续压字号更实际。
真要根治要在各模式内部把「最小字号」也做成可调，那是另一件事，不在本次范围。

### 13.14 挖孔避让的第二层：排版区（`RemotePlaybackStage`）

**问题**：§3.4 的「画布外扩」只把构图中心挪到了可见区中心，各 visualizer 的根容器仍是 normal flow
里的 `w-full` —— 布局盒子等于**加宽后的画布（453px）**，而不是可见区（242px）。于是主歌词按
453px 算可用宽度，一行排下来连穿摄像头竖带、再从右缘溢出屏幕。本地探针实测（347x212 / dpr
2.8125，安全带 105 CSS px）：

| 模式 | 侵入挖孔 | 右侧溢出 |
|---|---|---|
| `classic` | 90.3 px | 71.8 px |
| `partita` | 109.5 px | 24.2 px |
| `monet` | 85.0 px | 60.2 px |
| `pendolo` | 4.6 px（转轮最外圈那句贴左缘） | -0.2 px |
| `claddagh` / `cappella` / `still` | 21~27 px | 22~45 px |

**修法**：在画布里再套一层「排版区」——`absolute` 拔出 flow，左缘钉在安全带右边界，
右缘钉回屏幕右缘（`right: canvasExtraWidth`，不是 0：外层画布右缘在负偏移上，
取 0 会一路钉到加宽后的那条边，量出来还是画布宽）。布局盒子于是正好等于可见区宽，
`vw` / 百分比基准跟着落到看得见的那块区域上。这一层只管文字排版；背景仍由最外层铺满整屏
（含摄像头竖带），所以「整屏铺满、左侧无空缝」这个既有观感没有变。

**顺带修的两个真 bug**：

1. `VisualizerCappella` 用 `useStageViewport().width` 算气泡最大宽度，背屏拿到的是加宽后的
   画布宽而不是可见区宽，气泡因此冲出右缘。新增 `getStageViewportVisibleWidth` /
   `useStageViewportVisibleWidth`（=`visibleRight - visibleLeft`），cappella 改用它。
2. `pendolo` 的钟摆按「转轮中心 + 半径」定位，转轮最外圈的句子贴在可见区左缘外 4.6px。

**少数模式需要出厂构图例外**（`BUILTIN_REAR_LYRICS_FRAME_OVERRIDES`）：

| 模式 | 出厂例外 | 依据 |
|---|---|---|
| `partita` | fontScale 0.5 + scale 0.62 | 主字号下限 2.5rem = 40px 固定生效，分栏又是固定宽度，不折半就排不进 242px |
| `pendolo` | scale 0.62 | 转轮半径按 `min(w,h) * 0.42` 算，缩到 242 宽后最外圈越界 |

这两个值都是探针实测，不是估算；只在用户没为这个模式存过值时兜底，用户调过就一律以用户值为准
（取数逻辑收在 `resolveRearLyricsFrame(mode, stored)`，渲染入口 `RearLyricsApp` 与探针共用）。

**回归验证**：`node dev/probes/rearSafeAreaAudit.mjs <模式> 1 <输出json>` 会遍历真实文本节点，
输出每个块的落点、侵入深度，并区分「屏幕内侵入」与「屏幕外但越界」（后者不是遮挡，避免假警报）。
14 个内建模式在当前实现下 `visibleIntruders` 全为 0，且右缘均不超出 `innerWidth`。
